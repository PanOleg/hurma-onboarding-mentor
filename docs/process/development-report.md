## 1. Контекст і постановка задачі (06.10.2026)

**Вхідні дані.** Вакансія Full Stack Developer (PHP/Laravel + Vue) у Hurma System, HR SaaS з AI. Перший технічний дзвінок із Дмитром 07.10 о 12:10. До цього надіслано лист із шістьма продуктовими ідеями для Hurma. Вакансія вимагає щоденної роботи з Claude Code або Cursor, Spec-Driven Development і написання skills для AI-агентів.

**Що саме треба зробити.** Розробити одну корисну для Hurma фічу з нуля, фіксуючи кожен етап, зі схемами процесу й роботи фічі, на технологіях, які є в компанії. Фіча має працювати як доказ: кандидат працює через спеку, пише правила для агентів і думає в продукті Hurma.

**Аналіз задачі перед початком.** Три речі визначили подальші рішення.
1. Кейс дивитиметься тех лід Laravel-команди, а не продакт. Отже технічна глибина важливіша за кількість екранів.
2. Hurma single-tenant: дані клієнта ізольовані. Будь-яка AI-фіча має пояснювати, куди йдуть дані.
3. Стек Hurma за публічними даними: PHP (Laravel) + Vue, частково Python, MariaDB, Redis, Kubernetes/Helm, Docker, Jenkins, Prometheus/Grafana, Sentry. Усе, що можна взяти з цього списку, треба взяти, бо так Дмитро читає код у звичному контексті.

Локальне оточення на старті: PHP 8.4.13, Composer 2.8, Node 22, Docker 27.5, Redis 8, Claude Code 2.1. Директорія проєкту порожня.

### Критерії вибору

Що має запам'ятати тех лід після перегляду: «ця людина проєктує Laravel-системи з AI і тримає дані під контролем». За цим критерієм RAG-наставник дає найбільшу поверхню для демонстрації й найменше залежностей від сторонніх сервісів.

### Рішення

**Онбординг-наставник на RAG.** Скринінг не брали свідомо, щоб не робити «ще один AI Fox» наосліп, без даних Hurma. Кредити відкладені як можливий другий шар після наставника.

## 4. Технічні рішення фічі

### 4.1. Ембединги: чим рахувати вектори

Anthropic не має embeddings API, тому потрібен окремий провайдер.

| Варіант | Плюси | Мінуси |
|---|---|---|
| Voyage AI | партнер Anthropic, помітно кращий пошук, зокрема українською, безкоштовний стартовий ліміт | другий зовнішній вендор, якому йдуть документи клієнта; окремий ключ |
| OpenAI text-embedding-3-small | дешево й надійно | другий вендор, інший провайдер у проєкті |
| Локальна модель у Python-сайдкарі | документи не покидають інстанс (GDPR для single-tenant), показує Python зі стеку Hurma, нуль витрат | якість e5-small нижча за хмарні, образ Docker важкий, холодний старт |

**Рішення: локальна модель.** Аргумент «документи компанії не покидають інстанс» сильніший для single-tenant HR-продукту, ніж приріст якості пошуку на 20–50 документах. Дві умови пом'якшення: `fastembed` на ONNX замість PyTorch (образ менший, старт швидший) і інтерфейс `EmbeddingProvider`, щоб Voyage підключався драйвером. Модель `intfloat/multilingual-e5-small`, 384 виміри, а не bge-m3 на 1024: втричі менше місця, швидше, якості для кейсу достатньо.

### 4.2. Доступ до документів

| Варіант | Аналіз |
|---|---|
| Усі бачать усе | простіше, менше коду, але слабкий аргумент про безпеку HR-даних |
| Видимість за аудиторіями (всі, відділ, роль) | один Eloquent-scope і одна колонка, пів дня роботи; дає найсильніший негативний тест кейсу: «співробітник не бачить чужий документ» |

**Рішення: аудиторії.** Ціна мала, цінність для розмови з тех лідом велика.

### 4.3. Зв'язок Laravel і Vue

| Варіант | Аналіз |
|---|---|
| Inertia.js | робочий UI на день-два швидше, без налаштування Sanctum і CORS; API не видно окремо |
| REST API + Vue 3 SPA | дорожчий, але показує дизайн API, версіонування, ресурси; так влаштовані SaaS на Laravel + Vue, де фронт може жити окремо; SSE для стрімінгу природніший |

**Рішення: REST API + SPA.** Якщо на 7-й день фронт з'їсть час, Vuetify-компоненти лишаються ті самі, спростимо екрани, а не архітектуру.

### 4.4. Чат

| Варіант | Аналіз |
|---|---|
| Одне питання, одна відповідь | мінімум коду, виглядає як форма, а не продукт |
| Без стрімінгу, з історією | простіше, менше ризиків з проксі й таймаутами |
| Стрімінг + історія | три технічні ризики (буферизація nginx і PHP-FPM, таймаути, розрив з'єднання), саме про них питають бекендера на співбесіді; історія додає дешевий виклик Haiku |

**Рішення: стрімінг + історія.** Ризики працюють на кандидата. Якби треба було щось викинути, викинули б історію, а не стрімінг.

### 4.5. Межа між Laravel і Python

Ключове архітектурне рішення, розібране окремо, бо від нього залежить, що саме побачить тех лід.

RAG-пайплайн це шість кроків: витяг тексту, чанкування, ембединг, зберігання й пошук, генерація, пост-обробка. Питання лише в тому, яка мова володіє кожним.

| Підхід | Що в Laravel | Що в Python | Плюси | Мінуси |
|---|---|---|---|---|
| A. Laravel володіє RAG | документи, чанки, пошук із фільтром аудиторії в одному SQL, промпт, стрімінг, цитати, прогалини | лише `/embed` | одне джерело правди для домену; Pest-тести покривають весь ланцюжок з фейком замість Python; сайдкар замінний; показує саме Laravel, за який наймають | парсинг PDF у PHP слабший; чанкер писати руками |
| B. Python володіє RAG | користувачі, права, UI, збереження розмов | парсинг, чанкування, ембединг, пошук, виклик LLM | кращі інструменти парсингу; «чиста» мікросервісна межа | домен розривається: безпека даних залежить від того, чи Python правильно застосував фільтр; два світи тестів; ядро кейсу йде у другорядну мову; удвічі більше контрактів; стрімінг через два хопи |
| A з `/extract-text` у Python | як A | `/embed` і `/extract-text` (pymupdf, python-docx) | закриває головний мінус A ціною одного ендпоінта; домен і пошук лишаються в Laravel | сайдкар трохи більший |

**Рішення: A з `/extract-text`.** Фільтр аудиторії виконується в SQL до генерації, тому витік чужого документа неможливий у коді пошуку, і це доводиться одним Feature-тестом.

### 4.6. Рішення, ухвалені без окремого обговорення

- Sanctum через cookie для SPA, не токени: фронт на тому ж домені.
- Horizon для черг: дашборд добре виглядає на демо.
- Поріг релевантності 0.35 як стартовий параметр, калібрується на evals.
- Grounding-перевірка після відповіді, не блокує стрім: інакше користувач чекає два виклики.
- Промпти як версіоновані файли зі snapshot-тестами: зміна промпту видима в diff.

- Актуальні моделі й параметри API на жовтень 2026.

Під час планування з'явилися три факти, які змінили спеку. Кожен перевірений, а не припущений.

| Факт | Джерело | Наслідок |

| Laravel 13 вийшов 17.03.2026, потребує PHP 8.3+ | release notes, packagist | спека переведена з Laravel 12 на 13, щоб кейс не виглядав застарілим |
| Векторний індекс MariaDB працює лише з `ORDER BY VEC_DISTANCE_COSINE(...) LIMIT n` без інших умов | документація MariaDB | пошук у два кроки в одному SQL: індексований підзапит на 100 кандидатів, потім фільтр аудиторії й статусу зовні |

Спека завелика для одного плану, тому розбита на три за віхами:
- План 1 (дні 1–7): документи процесу, скаффолд, Compose, сайдкар, схема, інжест, пошук, стрімінгова відповідь з цитатами, мінімальний чат. 15 задач, кожна з тестами в тексті плану, кодом і командою перевірки.
- План 2 (дні 8–12): адмінка документів, retry, аудиторії в UI, історія, прогалини, статистика, видалення, rate limit.
- План 3 (дні 13–21): evals, Docker для app, Horizon, CI, runbook, сторінка-кейс, GIF, PDF.

Самоперевірка плану виявила й виправила до запуску: тести відповіді з фейковими векторами не пройшли б за порогом 0.35 (bag-of-words-вектори дають відстань 0.3–0.5, у тестах поріг піднято до 0.6 і тексти перетинаються словами); тест логіну потребує заголовка Referer для stateful-сесії Sanctum; у Vue-сторі мутація локального об'єкта після push не тригерить реактивність (виправлення передане в задачу 14).

## 7. Виконання плану 1: як саме працюємо

Спосіб виконання: subagent-driven. На кожну задачу окремий свіжий агент-виконавець, після нього свіжий агент-рев'юер із двома вердиктами (відповідність спеці і якість коду), раунди виправлень зі scoped-рев'ю, наприкінці рев'ю всієї гілки. Контролер не пише код сам, лише координує й ухвалює рішення, кожне рішення записане в журнал із тим, що воно коштує, якщо помилкове.

Альтернативою було виконання в одній сесії (швидше, дешевше, без незалежного рев'ю до кінця). Обрано subagent-driven, бо задачі зав'язані на інтерфейси одна одної, а рев'ю після кожної дає матеріал для журналу сесій, який сам є частиною кейсу.

Гілка `feat/plan-1-vertical-slice` в тій самій директорії, не worktree: репозиторій новий, IDE і Docker дивляться на цей шлях.
