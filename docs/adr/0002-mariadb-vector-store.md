# 0002. MariaDB Vector як векторне сховище

Дата: 2026-10-06. Статус: прийнято.

## Контекст

Hurma вже використовує MariaDB, тому окрема векторна база означала б ще одну систему для експлуатації та резервного копіювання. Чанки тісно пов'язані з документами та аудиторіями, а фільтр аудиторії має виконуватися в SQL до генерації. Обсяг даних для кейсу невеликий. MariaDB 11.8 має тип `VECTOR` і векторний індекс.

## Рішення

Чанки зберігаються в таблиці `document_chunks` із колонкою `embedding VECTOR(384) NOT NULL` і `VECTOR INDEX (embedding) M=8 DISTANCE=cosine`. Пошук виконує один клас `ChunkSearchRepository`.

## Альтернативи

| Варіант | Плюси | Мінуси | Чому відхилено |
|---|---|---|---|
| pgvector | Зрілий, багата підтримка фільтрів | Друга СУБД поруч із MariaDB | Додає систему в експлуатацію без потреби |
| Qdrant | Спеціалізований, швидкий, фільтри за метаданими | Окремий сервіс, дублювання прав доступу поза SQL | Фільтр аудиторії довелося б синхронізувати з реляційною базою |
| Meilisearch | Простий, є гібридний пошук | Векторна підтримка слабша, окремий сервіс | Поза межами v1 і не дає переваг для цього обсягу |

## Наслідки

Простіше: одна база, транзакції, join із `documents`, фільтр аудиторії в тому самому SQL. Складніше: векторний індекс MariaDB застосовується лише до запиту виду `ORDER BY VEC_DISTANCE_COSINE(...) LIMIT n` без інших умов. Тому пошук використовує підзапит кандидатів за індексом (`candidate_limit` 100), а фільтри аудиторії, статусу `ready` і soft delete застосовуються у зовнішньому запиті поверх нього. Безпека від K не залежить, але повнота залежить: якщо видимих документів мало, а кандидатів забагато чужих, результатів може не вистачити. Також Schema Builder не знає тип `VECTOR`, тому DDL міграції чанків пишеться сирим SQL (єдине місце поряд із `ChunkSearchRepository`). Моніторити: recall@5 на evals, значення `candidate_limit`, час пошуку.
