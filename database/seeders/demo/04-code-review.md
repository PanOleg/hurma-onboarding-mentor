# Процес code review у Vesna Tech

Цей документ описує, як в інженерному відділі Vesna Tech проходить рев'ю коду. Він призначений для розробників відділу Engineering. Мета рев'ю не в контролі, а у спільній відповідальності за якість коду та поширенні знань у команді.

## Принципи

- Код належить команді, а не окремій людині.
- Рев'ю це розмова, а не екзамен: коментуємо код, а не автора.
- Малі зміни рев'юються швидше та якісніше, ніж великі.
- Автоматичні перевірки беруть на себе рутину, а люди дивляться на сенс, дизайн і ризики.

## Розмір Pull Request

Ми дотримуємось простого правила: Pull Request має бути до 400 рядків змін. Це не включає згенеровані файли, залежності та файли блокування пакетів. Якщо зміна більша, розбийте її на кілька PR.

Чому це важливо:

- великий PR важко уважно прочитати, і рев'юер починає пропускати помилки;
- малий PR легше відкотити, якщо щось піде не так;
- швидке рев'ю тримає швидкість команди.

Як розбивати великі зміни: окремий PR для рефакторингу, окремий для нової функції, окремий для міграцій. Якщо розбити неможливо, попередньо обговоріть підхід із тімлідом і додайте до опису PR план читання.

## Опис Pull Request

Хороший опис економить час рев'юера. Він містить:

- що змінено і навіщо, з посиланням на завдання;
- як перевірити зміну локально;
- скріншоти для змін в інтерфейсі;
- відомі обмеження і те, що навмисно не зроблено.

Перед тим як просити рев'ю, перегляньте свій PR самостійно. Багато дрібниць видно одразу.

## Вимоги до злиття

Щоб PR можна було злити, потрібно виконати три умови:

1. Два апрува від колег із команди. Один апрув недостатній, навіть для малих змін. Принаймні один рев'юер має знати цю частину системи.
2. CI зелений: усі автоматичні тести, лінтери та статичний аналіз пройшли успішно. Червоний CI не обходиться, навіть якщо падіння здається випадковим; спершу виправте або перезапустіть тест і з'ясуйте причину.
3. Усі коментарі розв'язані або обговорені: ви або відповіли, або виправили код.

Автор PR не апрувить власний код. Зливає PR автор після виконання всіх умов.

## Терміни рев'ю

Рев'ю потрібно надати протягом 24 годин після того, як PR позначено готовим до перегляду. Це робочі години, тобто вихідні не враховуються. Ми вважаємо швидкий відгук частиною командної культури: людина, яка чекає на рев'ю, блокується.

Якщо ви не встигаєте, скажіть про це автору та запропонуйте іншого рев'юера. Якщо PR очікує довше, автор може нагадати у каналі команди або звернутись до тімліда.

## Як рецензувати

Під час рев'ю дивіться на таке:

- чи розв'язує код поставлену задачу і чи покриває граничні випадки;
- чи зрозумілий код без додаткових пояснень, чи доречні назви;
- чи є тести і чи вони справді перевіряють поведінку;
- чи немає проблем із безпекою, наприклад секретів у коді чи небезпечної обробки вводу;
- чи не ламає зміна наявну поведінку та сумісність.

Позначайте важливість коментарів. Префікс «nit:» означає дрібницю, яку можна не виправляти. Блокувальні зауваження формулюйте чітко: що не так і чому. Намагайтесь пропонувати варіант, а не лише критику.

## Як отримувати рев'ю

- Дякуйте за зауваження та не сприймайте їх особисто.
- Якщо не згодні, поясніть чому; за потреби покличте третього колегу.
- Не робіть у відповідь на рев'ю нових великих змін: вони потребують окремого PR.
- Після виправлень повідомте рев'юера, що PR готовий до повторного перегляду.

## Автоматичні перевірки

CI запускається на кожен PR і перевіряє:

- модульні та інтеграційні тести;
- форматування коду та лінтери;
- статичний аналіз типів;
- збірку фронтенду.

Усе, що можна перевірити автоматично, не потрібно обговорювати у коментарях. Якщо ви помітили повторювану дрібницю в рев'ю, запропонуйте додати для неї правило до лінтера.

## Термінові виправлення

Для критичних помилок у продакшені допускається прискорений процес: рев'ю протягом кількох годин, але два апрува та зелений CI залишаються обов'язковими. Після виправлення тімлід проводить короткий розбір причин, щоб не допустити повторення.

## Типові помилки

- Надто великі PR, які ніхто не хоче читати.
- Апрув без реального читання «щоб не блокувати».
- Тривале очікування рев'ю без нагадування.
- Змішування рефакторингу з новою функцією в одному PR.
- Відсутність тестів для виправлених помилок.

## Підсумок

- PR до 400 рядків.
- Два апрува.
- CI зелений.
- Рев'ю протягом 24 годин.
